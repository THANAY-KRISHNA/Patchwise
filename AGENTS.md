# Patchwise — Agent Guidelines & Project Rules

This document defines core behavioral constraints, development rules, and architectural standards for all AI coding agents and contributors working on the **Patchwise** codebase.

---

## 1. Core Operating Rules

1. **Follow the Approved Project Specification:**
   - Always adhere to the specifications in [`docs/Patchwise_Project_Report.pdf`](file:///docs/Patchwise_Project_Report.pdf) and [`docs/REQUIREMENTS_AND_IMPLEMENTATION_PLAN.md`](file:///docs/REQUIREMENTS_AND_IMPLEMENTATION_PLAN.md).
   - Preserve all defined features, requirements, architecture goals, evaluation methodology, security requirements, and dashboard designs.

2. **Technology Stack Discipline:**
   - **Frontend:** Use Next.js 14+ with **TypeScript** and Tailwind CSS / Vanilla CSS. Do not introduce untyped JavaScript.
   - **Backend:** Use **Python 3.11+** with **FastAPI**, Pydantic v2, and SQLAlchemy 2.0 with async PostgreSQL.
   - **Database:** PostgreSQL with structured migrations via Alembic.

3. **Keep Language-Specific Analyzers Modular:**
   - All language-specific analyzers must implement the pluggable `BaseLanguageAnalyzer` interface under `services/api/src/analyzer/`.
   - Core orchestration, GitHub retrieval, diff parsing, and database persistence must remain language-agnostic.
   - Adding a new language must never require refactoring core pipeline orchestration.

4. **Write Automated Tests for Every Major Feature:**
   - Provide unit tests for every new parser, rule, validator, and helper.
   - Provide integration tests for API endpoints and database operations using mock fixtures.
   - Run frontend component and page tests for user workflows.
   - Maintain the frozen evaluation benchmark (`benchmark/runner.py`) for quantitative regression detection.

5. **Never Hardcode Secrets or Commit `.env` Files:**
   - Never commit `.env` files, API keys, tokens, credentials, or private repository URLs.
   - Maintain placeholders only in `.env.example`.
   - Ensure all secrets (`GITHUB_TOKEN`, `LLM_API_KEY`, `DATABASE_URL`) are read exclusively from environment variables on the backend. Never expose secrets to frontend bundles or client logs.

6. **Run Tests and Report Actual Results Before Claiming Support:**
   - **Truth-in-Advertising:** Never claim a feature, language analyzer, or benchmark result works without running the test suite and reporting actual terminal output.
   - Do not use placeholder benchmark numbers as measured achievements.
   - Report language analyzer readiness accurately (`Active & Tested` vs `Planned / In Development`).

7. **Human-in-the-Loop & Destructive Change Approval:**
   - **Always ask for explicit user confirmation** before making destructive changes (e.g., dropping database tables, deleting core files, modifying git history).
   - **Always ask before installing unfamiliar dependencies** or running unvetted external scripts.
   - **Always ask before deploying publicly** to external cloud providers.

## 2. Review Engine & Provenance Mandates

1. **Three-Tier Finding Classification:**
   - `DETERMINISTIC_STATIC_ANALYSIS` (Tier 1): High-confidence, reproducible findings generated by deterministic rules or AST checkers.
   - `AI_GENERATED_HYPOTHESIS` (Tier 2): Potential bugs or patterns flagged by LLMs. Grounded in diff lines, but **never presented as a confirmed bug**—must be explicitly badged as an *unverified hypothesis*.
   - `VERIFIED_TEST_RESULT` (Tier 3): Findings validated by test suites or concrete test coverage verification.

2. **Strict Line Grounding:**
   - Every line-level finding must reference a valid line within the parsed diff hunk line set.
   - The validator must discard ungrounded line references or convert them to file-level scope.

3. **Zero Untrusted Code Execution:**
   - The backend is strictly a static text and AST analyzer.
   - Never execute arbitrary repository code, user-submitted build scripts, or untrusted tests on the application server.

4. **Prompt Injection Defense:**
   - Treat all PR code, commit messages, and descriptions as untrusted user input.
   - Structure LLM prompts to analyze the code without executing or following instructions embedded inside the code.
